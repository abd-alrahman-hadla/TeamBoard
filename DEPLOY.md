# Deploying TeamBoard

The public setup is four managed services, all with free tiers:

| Piece    | Service | What runs there                                                     |
| -------- | ------- | ------------------------------------------------------------------- |
| Web      | Vercel  | Next.js app; proxies `/api/*` to the API (same-origin cookies)      |
| API      | Render  | Docker image from `apps/api/Dockerfile` (NestJS + Socket.io)        |
| Database | Neon    | PostgreSQL                                                          |
| Pub/sub  | Upstash | Redis for the Socket.io adapter (needed once there are 2+ replicas) |

```
browser ──HTTPS──▶ Vercel (Next.js) ──/api/* rewrite──▶ Render (API) ──▶ Neon
   │                                                       ▲    │
   └──────────── WebSocket (Socket.io, direct) ────────────┘    └──▶ Upstash Redis
```

**Why REST goes through Vercel but sockets don't:**

- The refresh token is an httpOnly cookie. Through the rewrite, it is set on the Vercel origin (path `/api/auth`), so it's first-party. A cookie set by `*.onrender.com` would be third-party, and Safari and others block those.
- Socket.io authenticates with the access token in its handshake, not with cookies. Vercel can't proxy WebSockets, so the browser connects straight to Render (`NEXT_PUBLIC_SOCKET_URL`).

Everything below runs in this order. Expect about 30 minutes the first time.

## 1. Neon (database)

1. Create a project (Postgres 17 or 18, region close to your Render region, e.g. Frankfurt).
2. On the dashboard, copy two connection strings for the default branch:
   - **Pooled** (host contains `-pooler`): the API's `DATABASE_URL` at runtime.
   - **Direct** (no `-pooler`): migrations and the demo seed (`NEON_DIRECT_URL`, `DEMO_DATABASE_URL`).
3. Keep `?sslmode=require` on both.

> Prisma 7 with the `pg` driver adapter doesn't use named prepared statements, so the pooled (PgBouncer, transaction mode) URL should work. If you see prepared-statement errors in the Render logs, switch `DATABASE_URL` to the direct URL.

## 2. Upstash (Redis)

1. Create a Redis database (regional, same region as Render). Turn **TLS on**.
2. Copy the `rediss://default:<password>@<host>:6379` URL: the API's `REDIS_URL`.
   - Use **`rediss://`** with two s's (TLS). Upstash refuses plain `redis://`.
   - Don't use the **REST URL** (`https://….upstash.io`) or the REST token; those are for Upstash's HTTP API.
   - The API refuses a non-`redis(s)://` URL at startup. If it can't reach Redis within 15 s, it exits and logs `Could not connect to Redis at <host>…` in the Render logs.

> The Socket.io Redis adapter uses pub/sub, and presence uses `fetchSockets()` (a request/response over pub/sub with `PUBSUB NUMSUB`). Upstash supports these on regular Redis databases. Verify presence after the first deploy (step 6). If it's flaky, the API still works with `REDIS_URL` unset on a single instance (the adapter falls back to in-memory with a warning).

## 3. Render (API)

1. **New → Blueprint**, pick this repository. Render reads `render.yaml` and proposes the `teamboard-api` service.
2. Fill in the `sync: false` values:
   - `DATABASE_URL`: the Neon **pooled** URL.
   - `REDIS_URL`: the Upstash URL.
   - `WEB_ORIGIN`: your Vercel production URL. You don't have it yet: use `https://<project>.vercel.app` (the name you'll pick in step 4) and fix it later if needed.
3. `JWT_ACCESS_SECRET` is generated by Render. The blueprint also sets `COOKIE_SECURE=true`, `REFRESH_COOKIE_PATH=/api/auth`, `TRUST_PROXY=2` (Vercel's proxy + Render's load balancer) and `SWAGGER_ENABLED=false`.
4. `autoDeploy` is off: the deploy workflow migrates first, then deploys. Under **Settings → Deploy Hook**, copy the hook URL: that's `RENDER_DEPLOY_HOOK_URL`.
5. The first deploy needs the schema to exist, so run the migrations once from your machine before deploying (the workflow does this for later deploys):

   ```bash
   DATABASE_URL="<neon direct url>" pnpm --filter @teamboard/api db:deploy
   ```

   Then click **Manual Deploy** in Render. `/health/ready` turns green once the API reaches Neon.

> Free Render services sleep after 15 minutes without traffic. The first request after that takes about 30–60 s. Fine for a demo, not for production use.

## 4. Vercel (web)

1. **Add New → Project**, import the repository.
2. **Root Directory:** `apps/web`. Vercel picks up `apps/web/vercel.json` (pnpm install at the repo root, `turbo run build --filter=@teamboard/web`).
3. Environment variables (Production):

   | Name                     | Value                                | Why                                               |
   | ------------------------ | ------------------------------------ | ------------------------------------------------- |
   | `API_ORIGIN`             | `https://teamboard-api.onrender.com` | target of the `/api/*` rewrite (server-side only) |
   | `NEXT_PUBLIC_API_URL`    | `/api`                               | REST goes through the rewrite                     |
   | `NEXT_PUBLIC_SOCKET_URL` | `https://teamboard-api.onrender.com` | sockets connect straight to Render                |
   | `NEXT_PUBLIC_DEMO_MODE`  | `true`                               | shows "Try the live demo" on the login page       |

4. Deploy. If the production URL differs from what you put in `WEB_ORIGIN`, update it in Render and redeploy the API.

> Preview deployments get other URLs, which the API's CORS and Origin check reject. Use production for the demo, or point a separate API at your preview URL.

## 5. GitHub secrets and the demo data

In the repository: **Settings → Secrets and variables → Actions**:

| Secret                   | Value                   | Used by                                        |
| ------------------------ | ----------------------- | ---------------------------------------------- |
| `NEON_DIRECT_URL`        | Neon direct URL         | `deploy.yml`: `prisma migrate deploy`          |
| `RENDER_DEPLOY_HOOK_URL` | Render deploy hook      | `deploy.yml`: deploys after a green CI on main |
| `DEMO_DATABASE_URL`      | Neon direct URL (again) | `demo-reset.yml`: nightly demo reset           |

Then **Actions → Reset public demo → Run workflow** once. It creates:

- the "TeamBoard demo" workspace with the "Website launch" board;
- Sara (`sara.demo@example.com`) and Omar (`omar.demo@example.com`), password `teamboard-live-demo`, both MEMBERs;
- a non-login owner.

It runs again every night at 03:00 UTC.

Visitors can also reset it themselves: with `DEMO_MODE=true` on the API, the demo board shows a **Reset demo** button.

- It restores the board for everyone viewing it (open boards refresh live), and nobody gets signed out.
- It can be used at most once a minute.
- `render.yaml` sets `DEMO_MODE=true`. On a service created before it was added, set it by hand: Render → Environment → `DEMO_MODE` = `true`, then redeploy.

Without these secrets the deploy and reset workflows just print a notice and succeed, so forks stay green.

`ci.yml` pushes images to GHCR on `main` (`ghcr.io/<owner>/<repo>-api`, `-api-migrator`, `-web`). Render builds from the Dockerfile itself, so the GHCR images are for anyone running `docker-compose.prod.yml`-style setups elsewhere.

## 6. Verify

- [ ] `https://<render-host>/health/ready` returns `{"status":"ok", …}`.
- [ ] `https://<vercel-host>/api/health/live` returns 200 (the rewrite works).
- [ ] On the login page, "Sign in as Sara" opens the demo board.
- [ ] DevTools → Application → Cookies: `tb_rt` belongs to the Vercel host, path `/api/auth`, HttpOnly, Secure.
- [ ] Reload: you stay signed in (refresh through the rewrite).
- [ ] DevTools → Network → WS: one connection to `wss://<render-host>/socket.io/…`.
- [ ] Sign in as Omar in a private window: both avatars show in the header, and a card dragged in one window moves in the other.
- [ ] As Omar, comment `@Sara …` (pick her from the list): Sara's bell shows 1 without a reload.
- [ ] Rate limits see real client IPs. In the Render logs, request lines from two different networks (e.g. phone on mobile data and laptop) should not share a bucket. If every visitor appears with the same address, adjust `TRUST_PROXY`, which is the number of proxies in front of the API.

## Running the same thing on one machine

`docker-compose.prod.yml` runs the whole stack (Postgres, Redis, migrations, two API replicas, the web server, nginx) on `http://localhost:8090`. See the comments at the top of that file. The browser sees one origin: nginx mounts the API at `/api` and Socket.io at `/socket.io`.
